# 分布式连接的应用状态核对 · 2026-10-15

## 问题与观察

用户报告大屏 WorkBuddy、手机邮件。开始读取设备时，两边已恢复为 WorkBuddy；未捕获原始异常数据包，因此不能将某一种原因写成已经证实的根因。检查发现现有链路只依赖首次快照与后续增量，没有持续核对最后一次应用/焦点更新；漏掉最后一个增量后，若没有新操作，旧状态可长期留在手机。

## 修改

- 手机前台在分布式连接中每 1.5 秒发一个轻量版本探针，平板返回会话、版本、应用和目标的指纹。只在不一致或探针超时时拉取完整状态，不重发用户命令。
- 连接与回前台重新核对。完整同步带请求 ID；过期回复不能取消当前同步或将手机退回旧应用。更旧的探针结果不触发倒退。
- 等待完整同步时用“正在同步大屏应用”覆盖旧控制器，暂停远端写入；原编辑组件保留，受保护草稿不删除。12 秒未完成时显示可操作的重试入口与连接设置。
- 多个异常增量合并为一个同步请求；成功同步后恢复原来的普通增量路径。扫码网络模式沿用原协议。

## 验证

- 核心测试 122 项通过；TypeScript、生产 Web、两端签名 HAP 构建通过。
- 浏览器注入分布式桥：丢弃邮件→WorkBuddy 的最后一条更新后自动恢复；旧同步回复拒绝；更旧探针忽略；回前台、重复异常增量合并与断线后拒绝旧快照通过。连接方式面板两个回归也通过，共 4 项。
- 两端签名 HAP 覆盖安装成功；使用现有鸿蒙分布式重新配对。真机邮件→桌面→WorkBuddy，手机均跟随对应应用；点击平板新任务输入框后手机进入相同任务并保留原有草稿、颜色和草图。证据：`mail-follow.json`、`workbuddy-return.json`、`workbuddy-focus.json`、`final-workbuddy-input.json`。浏览器故障注入不替代真机传输证明。
- 额外两个浏览器回归通过：连接面板保持草稿/释放控制，以及润色选区、撤销和晚到结果保护；本轮浏览器共 6 项通过。
- 本轮未拔 USB 重新验收，也未修改当前 Gemini 密钥。
- 不改用户草稿、不发送任务、不更换 Gemini 密钥、不自动 push。

本轮证据放在忽略目录 `artifacts/distributed-sync/`。协议并未保证所有网络负载无延迟；大材料的完整快照仍需时间。长期压力及拔 USB 后的本轮重新验收单独记录。
