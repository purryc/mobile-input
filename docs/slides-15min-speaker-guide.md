## 口播与转场

### 1. 系统级手机输入 / 随应用与任务 / 切换输入面板（0:10）

让手机成为随任务变化的大屏输入面板。

**转场：** 先看现有方案解决了什么，还留下哪些成本。

### 2. 竞品分析：表达、控制与任务协作的能力边界（0:50）

Typeless 帮助整理表达，TourBox 提供专业副手控制，Stream Deck 集中重复操作，Agent 伴随工具帮助处理任务。它们已有明确价值，但仍存在配置、目标切换、额外设备和人工接续成本。我们需要验证：手机按当前任务提供输入，是否能减少这些成本。

**转场：** 这些成本具体落在哪些人身上？

### 3. 用户需求：高效表达、连续创作与跨任务操作（0:45）

文档输入量大，创作频繁切工具，多 Agent 协作要跨平台补要求和材料，娱乐依赖配件或难够到的大屏触控。这里只讲现状。

**转场：** 同样四类人，手机分别能接住哪些操作？

### 4. 产品方案：以手机承载大屏场景的输入与控制（0:30）

文字表达、创作副手控制、Agent 请求介入、媒体与游戏遥控。大屏继续承载结果，手机帮助完成当前操作。

**转场：** 先看一段完整的双屏体验。

### 5. 双屏协同演示：手机输入，大屏同步操作（1:30）

先看这段已有的 84 秒双屏录屏，再拆解具体场景。播放期间不重复讲解。

**转场：** 下面用场景地图定位刚才的体验。

讲者提示：现有原型录屏不代表全部第三方应用已完成原生接入。

### 6. 应用场景：文本、Agent、专业操作与娱乐（0:15）

四类场景分别是文本表达、Agent 任务、专业应用控制和娱乐。图标说明可覆盖的方向，不代表所有应用已经接入。

**转场：** 接着看用户怎样进入这套输入方式。

### 7. 输入启用：多入口激活，面板跟随当前应用（0:30）

文本框、虚拟键盘和任务栏是明确入口。已连接的适配文本框可直接激活；桌面或键盘请求在手机确认。物理碰屏是目标设计，不能把点击原型当成已实现。

**转场：** 启用之后，先看最普遍的文字输入。

### 8. 场景化文本优化：按字段用途推荐润色方式（0:45）

聊天强调自然与简短；邮件强调商务表达和诉求；文档关注规范表达，演示关注标题；Agent 指令强调需求与要点。按实际字段选择最多三个入口。只修改当前字段或选区，保留原意，不发送。

**转场：** 有些要求仅靠润色还说不准，需要参数或材料。

### 9. Agent 辅助输入：识别指令中的参数与材料需求（0:55）

同一份公司 Roadmap 任务仍在输入阶段。句内入口由已表达的颜色与布局意图产生，用户打开工具再调整。颜色实时更新当前参数，手绘确认只采用草图。最后明确发送才提交任务。

**转场：** 提交后的任务，也可能需要用户再做决定。

### 10. Agent 人工决策：批准、拒绝、做选择与补充要求（0:40）

Agent 需要人介入时，手机承接三类请求。第一类，执行前批准或拒绝，例如是否追加票据。第二类，选择方案，例如产品介绍 PPT 面向客户、内部团队还是投资人；选中并确认后回复。第三类，补充要求，例如控制在八页内、突出产品价值。三类按需出现，不是连续步骤；补充和选择都不代替执行授权。

左侧为现有票据任务本地 Demo 截图。审批复用现有设计，PPT 选择与补充为设计补充，未接入运行。

转场：换到 WPS，看当前对象变化怎样改变手机面板。

### 11. PPT 场景适配：按编辑对象与放映状态切换面板（1:00）

同一份 PPT 的五种状态：没有对象、空文本框、文字选区、多对象、放映。依次看大屏目标与手机操作，重点比较文字格式和多对象对齐。放映直接用专用预设。大屏来自真实 Mac WPS，手机为对应设计稿；两者说明目标映射，不证明鸿蒙跨端控制已接通。

**转场：** Word 结构简单，但仍使用同一套判断。

### 12. Word 编辑适配：同步正文，按选区提供编辑操作（0:30）

已有光标的空正文是有效编辑目标。输入时同步正文与润色，选区时格式和改写作用于选区。普通正文不增加发送按钮，保存仍是独立动作。

**转场：** 除了文字，手机也能承担连续控制。

### 13. 专用场景控制：绘画工具、媒体遥控与游戏手柄（0:25）

绘画保留主手创作，手机副手调节；媒体观看与遥控分离；游戏使用固定手柄。操作中不因推荐突然换位。

**转场：** 除了当前操作，同一内容还可能引出下一步。

### 14. 上下文推荐：基于当前消息提供回复与服务入口（0:35）

看同一条微信会议消息：回复建议与服务入口同时存在。回复采用进入同一草稿，不发送，也不表示同意安排；服务选择并成功打开才变成当前操作，明确执行才创建。自行输入收起回复建议，服务失败保留草稿。

**转场：** 这些体验由同一条判定流程组织。

### 15. 场景判定：当前操作与上下文服务并行决策（1:10）

建联启用后并行判断当前输入与上下文服务。应用控制优先预设；普通文本区分空稿回复与已有正文润色；Agent 输入可以目标清楚但仍需要参数；已选任务按真实请求展示。服务成功打开重新成为当前操作。系统事实直接用，语义问题才交给 Jev。

**转场：** 判断完要提供什么，还需要保证操作位置稳定。

### 16. 面板布局：固定顶部与底栏，中部承载场景操作（0:35）

两张手机图是同一任务、同一内容，只改变触控板状态。上部身份与连接稳定，中部按目标变化，下部常用输入可展开收起。展开让中部让位，草稿、材料和手动偏好保留。

**转场：** 接下来说明这些界面如何从已有资产组合出来。

### 17. 面板生成：优先复用预设，按能力组合组件（1:50）

先看上方：系统读取应用、模式、焦点、选区和能力，再判断有没有适用的完整场景预设。预设优先，信息不足时保留基础输入。

左侧 A 是游戏：匹配后直接调用已有完整控制器，绑定应用和控制能力，方向键与动作区按既定布局使用。它不经过右侧的控件挑选和临时组合；放映等适用专用预设也走这条路径。

右侧 B 是本例 WPS 文字选区：没有匹配的完整预设时，按合法能力配置 Button、Stepper、Chip 等控件，组成同一选区的文字格式操作，再放入完整手机面板的中部。应用目标区和输入底栏仍保持稳定。只有需要语义匹配时才调用 Jev，它不能创造新能力。

两条路径共享 Design Token、Icon、本地校验及执行回读。没有绝对值回读时只提供相对控制；Slider 仍须具备当前值、范围、步长、设值与回读。图示不代表通用组合器或原生绑定已完成接入。

**转场：** 最后按真实依赖排落地顺序。

### 18. 实施优先级：基础输入、单应用生成与跨应用扩展（1:05）

先做连接、目标识别、同步编辑和应用执行回读，再用 WPS 验证单应用三层生成。随后扩展润色、Agent 参数与请求，最后逐应用扩展服务。难度按真实端到端实现评估，P0 等为本轮建议，不是已确认排期。

**转场：** 保留一分钟缓冲用于问题。
